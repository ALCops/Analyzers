# PC0030: UsePartialRecordsForLoops

## Purpose

Recommends `SetLoadFields` (or `AddLoadFields`/`SetBaseLoadFields`) before a read on a local record that drives a `Next()` loop. A loop fetches every row it visits with every normal field, including table-extension fields; loading only the fields the loop reads makes it several times faster. Single-record reads are not reported: they gain nothing, and repeated non-primary-key single reads lose the server record cache under partial records.

Registers `RegisterCodeBlockAction` on method/trigger bodies; main type `UsePartialRecordsForLoops` with the `LoopReadWalker` operation walker.

## Design decisions

| Decision | Rationale |
|---|---|
| Report loop reads only, not every read | Measured on BC 29.1 ([#531](https://github.com/ALCops/Analyzers/issues/531)): loops over many rows are 5-8x faster with `SetLoadFields`, single-record reads gain nothing, and repeated single reads that are not full-primary-key lookups bypass the NST data cache (60-90x slower). The dividing line is loop versus single record, not `Get` versus `Find*`. Breaking change in what the rule reports, accepted; ID and help URL kept |
| Entry reads are every buffer-filling read: `Find`, `FindFirst`, `FindLast`, `FindSet`, `Get`, `GetBySystemId`, any `Find` argument; `IsEmpty`/`Count` are not entries | Every entry method measured ([suite G](https://github.com/ALCops/Analyzers/issues/531#issuecomment-7081224298): FindSet, `Find('-')`, `Find('+')`+`Next(-1)`, FindFirst, FindLast+`Next(-1)`, Get) gave the same gain once a `Next` loop followed, and `FindSet` without a loop behaved like a single read: the `Next` loop is the only signal. `GetBySystemId` is included by analogy with `Get`. The set is a class constant of its own, not shared with PC0031, which needs every read kind |
| Pending/confirmed pairing: an entry read is pending; a built-in `Next` on the same variable inside a loop moves the pending reads made outside that loop to confirmed; only confirmed reads are reported | Pairs the read with the loop it drives without pattern-matching `if FindSet then repeat`: it covers `if not FindSet then exit; repeat`, `while Next <> 0`, `until (Next = 0) or Stop`, `Next` as a statement in a `while` body, reads in either branch before one loop |
| Loop-depth rule: each read records the number of enclosing loops (`repeat`/`while`/`for`/`foreach` bodies and the `repeat`/`while` condition, which run every iteration; not the `for` bounds or the `foreach` collection, which run once before the loop); `Next` at depth d confirms pending reads with depth < d; a `Next` outside every loop confirms nothing | `repeat Get(..) until Next = 0` must not count the `Get` as the driver, and `FindFirst(); Next();` is a cursor step, not a loop. A new entry read on the variable drops its pending reads at the same or deeper level (the cursor moved), so `FindFirst(); FindSet(); repeat` reports only `FindSet`, while a read inside the loop body never discards the shallower driver outside it: `V.FindSet(); repeat V.Get(V.Parent); ... until V.Next() = 0` still reports the `FindSet`, because the loop still reads its rows through `Next` and the per-iteration full-key `Get` stays cached with or without partial records |
| Leaving a loop drops the pending reads made inside it (depth greater than the depth after the loop); confirmed reads stay | A read inside a loop body is never a driver, so it must not survive the loop and be confirmed by a `Next` in a later, more deeply nested loop: `for i := 1 to 3 do V.Get(i); ... while Foo do while V.Next() <> 0 do` would otherwise report the `Get` |
| `Next` is matched as a built-in method on the receiver, for `Record` and `RecordRef` alike | User procedures named `Next` on a table are calls on the record and suppress like any table procedure |
| Syntax pre-filter: the body is bound only when an identifier token named `Next` occurs | Complete by construction (no `Next`, no confirmed read) and skips almost every body before `GetOperation` |
| Writes, table procedures, passing the variable as a bare argument, whole-record assignment with the variable as source, and `exit(Rec)` clear pending and confirmed reads on the current path retroactively; all but `exit` also block new reads on the path | Adding `SetLoadFields` before the loop would make the later full-record operation JIT-load or hand a partial record to code that may read any field. `exit` ends the path, so a forward flag would only leak suppression past the enclosing branch through the OR-merge |
| A load-fields call after the read (`FindSet(); SetLoadFields(...); repeat ... until Next() = 0`) does not cover it; `HasLoadFields` only blocks reads that follow it | The read already opened the result set with every column, and the loop iterates that result set; the call has to precede the read to change what is fetched |
| `Clear(V)` resets the flags and drops pending reads, keeps confirmed ones; assigning another record to it (`V := Other`) drops pending reads too and leaves the flags; `V.Reset()` resets the flags only; `SetLoadFields()` without arguments resets `HasLoadFields` | A cleared or overwritten variable has no cursor of its own left to loop over, but a loop that already ran on it stays a finding. `Reset` keeps the position, so a pending read can still drive a loop; that it clears `HasLoadFields` is documented runtime behaviour: `Reset` "removes all filters ... changes fields select for loading back to all" ([Record.Reset](https://learn.microsoft.com/dynamics365/business-central/dev-itpro/developer/methods-auto/record/record-reset-method), the same for `RecordRef.Reset`) |
| `RecordRef.SetTable(...)` (any overload) counts as a write on the `RecordRef` | Replaces the old linkage to the target record's state with the simplest conservative rule: the copied record is then used as a whole. `GetTable`, `Open`/`Close` are ignored |
| Fork/merge at `if`/`case`/`while`/`for`/`foreach` (the latter three merge pre-loop and post-body state), `repeat` body then condition without a fork. `HasLoadFields` merges with AND, the other flags with OR; both read lists keep pre-fork reads only when every branch kept them and union reads added inside a branch, deduplicated by `SourceSpan.Start` | Intersection lets a branch that wrote the record clear a read made before the fork; union keeps a loop driven from either branch. Without the dedupe nested branches doubled the list per level and threw `OutOfMemoryException` on the Base App |
| `RecordRef` locals are tracked and reported although the CodeFix is not offered for them | `RecordRef.SetLoadFields` exists and takes field numbers, which the developer can supply even though the fix cannot determine them; the old rule reported `RecordRef` reads the same way |
| Setup and reference tables are not tracked | Few-row tables read often are exactly the case that loses the NST record cache: `SetLoadFields` bypasses it and re-queries SQL every time ([#531](https://github.com/ALCops/Analyzers/issues/531), [#297](https://github.com/ALCops/Analyzers/issues/297), Duilio Tacconi above). Recognizer `TableHelper.IsSetupOrReferenceTable`, signals cheapest first: a single Code-type PK field named `Primary Key`/`PrimaryKey` (the setup heuristic, [#283](https://github.com/ALCops/Analyzers/issues/283)/[#287](https://github.com/ALCops/Analyzers/issues/287)), `Code` or `Name` (~90% precision on w1-28.4); a namespace ending in `.Setup` (structural, via `GetContainingNamespaceQualifiedNameWithReflection`; ~90% precision); a parameterless `GetRecordOnce` method. Any `AutoIncrement` field in the primary key vetoes the match (growing log-style tables in a Setup namespace; checked on every PK field so a compound `Code, "Entry No."` key is caught too). Field count, table-name suffixes and per-call context rejected: field count is meaningless (General Ledger Setup has 114 fields and one row), names are locale-dependent, context is cross-method. `IsSetupTable` stays separate for AC0013 (`FieldGroupsRequired`), which relies on its narrower meaning |
| Local variables only, including the synthesized `Rec` local of a `TableNo` codeunit `OnRun`; bound receivers must be `SymbolKind.LocalVariable` before the name-keyed map is consulted | Globals need cross-method analysis and parameters the calling context. `this.<Global>` and `this.<DataItem>` reach an object-scope symbol that may share the local's name; a bare identifier always binds innermost, so text lookups for arguments stay name-based |
| Severity Info; version gate `Spring2021OrGreater` (runtime 6.0, BC17); full netstandard2.1 support | Loop frequency and row count are unknowable statically, so the finding stays a suggestion. `SetLoadFields` arrived with runtime 6.0 |
| Complement to CodeCop AA0242: fires only when `SetLoadFields` is entirely absent on the path | AA0242 covers a present `SetLoadFields` that misses accessed fields |

## Deliberate non-reports

- Every single-record read (`Get`, `GetBySystemId`, `Find`, `FindFirst`, `FindLast`, and `FindSet` without a `Next` loop): no gain, and a cache loss when repeated.
- `Next` outside every loop (`FindFirst(); Next();`): a cursor step, not a loop.
- Reads inside the body of their own loop (`repeat Get(..) until Next() = 0`, `Get` per iteration of a `for`/`while`/`foreach`): repeated single reads, the case that loses the cache.
- Reads on another variable inside a loop (`Item.Get` inside a Customer loop): single reads of that variable.
- Report and query dataitem loops: the runtime drives them, there is no `Next` in the code (and dataitems are not locals).
- Global variables, parameters, temporary records, non-SQL table types (CDS, Exchange, ...), setup and reference tables.
- Variables written, passed on, assigned from or returned on the path (`FindSet` loop with `Modify`, `exit(Rec)` inside the loop).
- `Rec`, `this` and bare self forms inside tables and tableextensions: object-scope globals, never in the local map.

## Known issues

- Small loops that run very often (a few rows per call) lose the NST cache just like repeated single reads; the row count cannot be known statically, so they are still reported. Setup and reference tables are excluded as the common case.
- Single pass over loops, no fixed point: a `Next` in a `while`/`for` body confirms reads made before the loop, but state changes late in a loop body do not flow back to its start.
- A read made before an `if`/`case` and superseded by a newer read in only one branch is dropped at the merge: `Customer.FindFirst(); if Flag then Customer.FindSet(); repeat ... until Customer.Next() = 0;` reports the `FindSet` only, and the loop driven by `FindFirst` on the other path goes unreported. Accepted: the loop is still reported once, and telling "superseded" from "cleared" at the merge is not worth the extra state for this shape.
- Any write method on the variable after the loop, including `Init`, `ModifyAll` and `DeleteAll` when the variable is reused (`... until Item.Next() = 0; Item.Init(); Item.Insert();`), clears the loop finding retroactively. The same conservative rule the rule has always applied, kept because the partial buffer could then feed a write.
- `LoopReadWalker` inherits the SDK `OperationWalker` gap for `is`/`as`/conditional expressions and the Instance-carrying access kinds: a tracked record passed to a procedure inside such an expression does not set `PassedToFunction`. The audit of every walker is tracked in [#642](https://github.com/ALCops/Analyzers/issues/642).
- Namespace false positives of the setup recognizer: the `AutoIncrement` veto removes `Payment Reporting Argument` and `Adv. Bonus Depreciation Setup`; `Close Income Statement Buffer`, `Inventory Period Entry` and `Warehouse Employee` (compound Code/Date keys, no `AutoIncrement`) stay recognized although they grow. Accepted: the rule merely goes quiet (missed advice, never harmful advice).
- Compound-PK reference tables outside `.Setup` (`Inventory Posting Setup`, `Dimension Value`, `Currency Exchange Rate`, posting setups in a partner namespace) and small tables with a single Code PK named `No.` (`Resource Group`, `Item Charge`) are not recognized and still report when looped over. Accepted: the `No.` shape is master data or document headers throughout the Base App, and a compound-PK signal without name matching does not exist.

## SDK facts

- `V.Next` without parentheses binds as an `IInvocationExpression` (fixture `NextWithoutParentheses`), and `RecordRef.Next` has `MethodKind.BuiltInMethod` (fixtures `LocalRecordRefFindSetLoop`, `RecordRefNextLoopAfterOpen`).
- `ISymbol.ContainingNamespace` is available at all four SDK reference versions (ns2.0 12.0, net8 16.0, net10 18.0.36 and latest). Referenced modules rebuild their namespace tree from the symbol package (`ReferenceModuleSymbol.BuildNamespaceTree`), so Base App tables referenced from a partner app carry their namespace. A null namespace (pre-namespace runtimes) means the signal is absent, not a false match.
- `Next` is not a keyword: it is lexed as an `IdentifierToken` (`SyntaxKind.cs` in `../nav-sdk-source` has no `NextKeyword`), which the pre-filter relies on.

## Test notes

- The `this` fixtures are gated on runtime 14.0 (`SkipTestIfVersionIsTooLow`).
- HasFix fixtures keep their insertion scenario with the read in loop form; a read embedded in a `while`/`for`/`foreach` body uses the `if FindSet() then repeat` form, because a loop after the enclosing loop sits at the same depth and confirms nothing.

## CodeFix: UsePartialRecordsForLoopsCodeFixProvider

| Decision | Rationale |
|---|---|
| `Record.SetLoadFields(...)` goes immediately before the read's own statement (Common `FindStatementInsertionTarget`): a statement in a statement list (`BlockSyntax`, `RepeatStatementSyntax.Statements`, `CaseElseSyntax.ElseStatements`) gets an insert before it; one embedded as the single statement of an if/else branch, case line, `while`/`for`/`foreach`/`with` body is wrapped in `begin SetLoadFields; <statement> end`, including else-if chains (`end else begin`) | Matches the MS Docs convention. Climbing to the nearest `BlockSyntax` child instead put the call before a distant `repeat`, `case` or `if`, outside the branch that reads |
| A read in a loop or if condition targets the loop or if statement itself. `asserterror` is not an embedding parent: a single embedded body is never wrapped and the climb continues to the `asserterror` statement; a body that is already a block (`asserterror begin ... end`) takes the insert inside it like any block | The call must run before the condition is evaluated; wrapping a single `asserterror` body would put the call under `asserterror` |
| Custom `FixAllProvider.Create` that applies every edit through one `SyntaxEditor` (Common `SyntaxEditorExtensions.InsertStatementsBefore`); the single fix runs the same path | Nested reads (`if A.FindSet() then ... if B.FindSet() then`) give nested wraps whose edits overlap, and `BatchFixer` drops all but one of them. The editor tracks every edited node and hands each replacement the already rewritten target, so an outer wrap and an inner wrap or insert compose in any order. Edits are grouped by target statement and deduplicated by variable symbol (two reads of one variable in one statement get one call, the same variable in two branches gets one per branch), ordered by read position. The fix always starts from `GetDocumentDiagnosticsAsync`: the SDK passes empty `fixAllSpans` for every scope (`FixAllState.GetFixAllSpansAsync`, same at 12.0, net8 and net10), and any non-empty spans only filter those diagnostics by intersection |
| Fix All inserts one `SetLoadFields` per reported read, so two sequential loops on one variable get two calls (`HasFixAll/SameVariableInTwoStatements`); applying single fixes one after another stops after the first, because the first call then covers the second read on the path | Accepted: the second call is redundant, not wrong, and keeps each loop's call next to its read |
| No fix when the statement to wrap `ContainsDirectives` (active or inactive `#if`, `#pragma`); directives outside it are preserved (Common `BlocksStatementInsertion`) | Wrapping rebuilds the statement and moves its trivia; preserve-or-bail policy. Outside the statement, a wrap replaces only the whitespace before a following `else`, and only when it is pure whitespace: without that check an `#if` before the `else` was dropped and its `#endif` left unbalanced. An insert lands before the target's leading trivia, so it is not offered either when the target's first token carries a directive: an `#if` guarding the read (or the `#endif` of a preceding block) would leave the call on the other side of it, running unconditionally. The formatter pass re-indents a directive that leads the token after the block (`#endregion` gets the code's indentation), as Format Document would |
| `RegisterCodeFixesAsync` only resolves the read and its target statement; the field list is collected when the action runs, and the document's line break is looked up once per pass | Collecting fields walks the method body's operation tree, which the lightbulb query does not need |
| Wrap trivia, one rule for every wrap: the block takes the statement's leading and trailing trivia and, when the statement ended with `;`, its own `;`; the wrapped statement keeps neither, and the `end` keyword gets the document's line break (`GetLineBreak`) | The CodeAction formatter (`Formatter.Annotation` on the block) re-indents the wrapped statement and nested lines, but `SyntaxFactory.Token` is elastic on both sides and the elastic rule turns an elastic gap before `end` into a blank line. Moving the trailing trivia behind the block puts a trailing line comment after `end;`: the lexer leaves the line break after a line comment to the next token, so a comment kept inside would sit directly before `end` and comment it out |
| A then-branch followed by `else` puts the `else` on the `end` line (`end else`) only when whitespace alone separates them: the wrap drops the final line break of the moved trailing trivia, and the if statement's `else` keyword gets elastic leading trivia | The formatter only adds line breaks (`else` has `PreserveLines(0)`), so the join must come from the edit. The elastic `else` also brings the pair after `else` into the formatted span, which puts a same-line else branch (`then A.FindSet() else exit('')`) on its own line. A comment or directive there stays and the `else` keeps its own line |
| `Record` variables only, not `RecordRef` | `RecordRef.SetLoadFields` takes integer field numbers that are not statically determinable |
| Field list = Normal fields whose values are consumed in the method body, resolved in the CodeFix via `Document.GetSemanticModelAsync()`; sorted alphabetically (case-insensitive) | Zero analyzer overhead; deterministic output regardless of source order. The collector walks the whole method body, so fields used before the read or by an unrelated loop on the same variable are included too; over-inclusion is harmless (a loaded but unused field costs nothing measurable) and keeps the fix deterministic. FlowField, FlowFilter and Blob are skipped because `SetLoadFields` returns false for them |
| Two built-in selector sets are excluded from consumption: first-argument selectors (`SetRange`, `SetFilter`, `GetFilter`, `FieldCaption`, ...) and all-argument selectors (`SetCurrentKey`, `AddLoadFields`, ...); `TestField`/`FieldError` remain consumers | A field named as a filter or key selector is not read from the buffer, but a field passed as a filter *value* (`SetRange(F1, MyTable.F2)`) is. Only built-in methods are excluded because user-defined calls already suppress the diagnostic |
| Fallback to primary-key fields when no consumed field is found (including all-selector cases) | Establishes the partial-records pattern; PK fields are always loaded |
| Field and method receivers are matched by symbol identity with the diagnosed variable (`GetSymbolSafe()` then `Equals`), not by name | A `this.<Global>` receiver can share the local's name; name matching put the global's fields into the generated `SetLoadFields` list |
| The `SetLoadFields` receiver reuses the read's receiver expression (`WithoutTrivia()` plus a leading `SyntaxFactory.ElasticMarker`) instead of rebuilding it from the symbol name | Keeps the source spelling, quotes and casing (`"my table".FindSet()` gets `"my table".SetLoadFields(...)`); the elastic marker lets the CodeAction formatter indent the inserted statement. Same approach as the PC0035 fix |
| No fix for a read spelled without parentheses (`MyTable.FindSet;`), although the diagnostic is reported | Its syntax is a `MemberAccessExpressionSyntax` and the fix resolves only an `InvocationExpressionSyntax`; CodeCop AA0008 asks for the parentheses anyway (fixture `NoFix/ReadWithoutParentheses`) |
